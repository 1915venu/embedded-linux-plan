PHASE 7: SPI + BUILD SYSTEM + FINAL PREP (Days 36-40)

DAY 36: SPI BASICS

Theory: What is SPI?

SPI (Serial Peripheral Interface) is a synchronous, full-duplex communication protocol commonly used for high-speed peripherals like flash memory, displays, ADCs, and DACs.

SPI Signal Lines:
  MOSI  — Master Out Slave In  (data from master to slave)
  MISO  — Master In Slave Out  (data from slave to master)
  SCLK  — Serial Clock         (generated by master)
  CS/SS — Chip Select          (one per slave, active low)

Full duplex: data flows both directions simultaneously on every clock edge.

Theory: CPOL and CPHA

SPI has four modes defined by Clock Polarity (CPOL) and Clock Phase (CPHA):

CPOL=0: Clock idles LOW
CPOL=1: Clock idles HIGH

CPHA=0: Data sampled on first clock edge
CPHA=1: Data sampled on second clock edge

Mode 0 (CPOL=0, CPHA=0) — most common
Mode 1 (CPOL=0, CPHA=1)
Mode 2 (CPOL=1, CPHA=0)
Mode 3 (CPOL=1, CPHA=1)

The slave’s datasheet tells you which mode it requires. If the mode is wrong, every byte you read is garbage.

Theory: SPI vs I2C

Feature I2C SPI
Wires 2 (SDA, SCL) 4 per device (MOSI, MISO, SCLK, CS)
Speed 100kHz / 400kHz / 1MHz 10MHz to 100MHz+
Full duplex No Yes
Addressing 7-bit or 10-bit address Chip Select line
Multi-device Many on same bus One CS line per device
Typical use Sensors, EEPROMs, RTCs Flash, displays, ADCs, fast sensors

Interview rule of thumb: Choose I2C when wire count matters and speed is not critical. Choose SPI when speed matters or the device needs full-duplex communication.

Theory: Linux SPI Driver Model

Linux SPI follows the same master-controller / device structure as I2C:

SPI subsystem:

  struct spi_master    — the SPI controller (hardware bus)
  struct spi_device    — a device on the SPI bus
  struct spi_driver    — driver that handles a spi_device
  struct spi_transfer  — one segment of a SPI transaction
  struct spi_message   — a sequence of transfers (atomic on the bus)

SPI messages are composed of one or more transfers. Each transfer describes bytes to send, bytes to receive, and delay settings.

Theory: Device Tree for SPI Devices

SPI devices are described as children of the SPI controller node:

&spi0 {
    status = "okay";

    my_sensor: sensor@0 {
        compatible = "vendor,my-spi-sensor";
        reg = <0>;                 /* chip select 0 */
        spi-max-frequency = <1000000>;
        spi-cpol;                  /* optional: CPOL=1 */
        spi-cpha;                  /* optional: CPHA=1 */
    };
};

reg is the chip-select number (0, 1, 2…), not a memory address as in platform drivers.

Theory: SPI Driver Skeleton

#include <linux/spi/spi.h>
#include <linux/module.h>
#include <linux/of.h>

struct my_spi_dev {
    struct spi_device *spi;
    /* per-device state */
};

static int my_spi_probe(struct spi_device *spi)
{
    struct my_spi_dev *dev;

    dev = devm_kzalloc(&spi->dev, sizeof(*dev), GFP_KERNEL);
    if (!dev)
        return -ENOMEM;

    dev->spi = spi;
    spi_set_drvdata(spi, dev);

    /* Configure SPI mode if needed */
    spi->mode = SPI_MODE_0;
    spi->bits_per_word = 8;
    spi_setup(spi);

    dev_info(&spi->dev, "SPI device probed\n");
    return 0;
}

static void my_spi_remove(struct spi_device *spi)
{
    dev_info(&spi->dev, "SPI device removed\n");
}

static const struct of_device_id my_spi_of_match[] = {
    { .compatible = "vendor,my-spi-sensor" },
    {}
};
MODULE_DEVICE_TABLE(of, my_spi_of_match);

static struct spi_driver my_spi_driver = {
    .driver = {
        .name           = "my-spi-sensor",
        .of_match_table = my_spi_of_match,
    },
    .probe  = my_spi_probe,
    .remove = my_spi_remove,
};
module_spi_driver(my_spi_driver);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("SPI sensor driver skeleton");

Theory: SPI Transfer Example

/* Write one byte, read one byte (full duplex) */
static int my_spi_transfer(struct spi_device *spi, u8 tx, u8 *rx)
{
    struct spi_transfer t = {
        .tx_buf = &tx,
        .rx_buf = rx,
        .len    = 1,
    };
    struct spi_message m;

    spi_message_init(&m);
    spi_message_add_tail(&t, &m);
    return spi_sync(spi, &m);
}

/* Or use the simpler helper for read-after-write */
static int my_spi_write_then_read(struct spi_device *spi,
                                   const u8 *txbuf, unsigned txlen,
                                   u8 *rxbuf, unsigned rxlen)
{
    return spi_write_then_read(spi, txbuf, txlen, rxbuf, rxlen);
}

Interview Questions — SPI

Q: What is the difference between I2C and SPI?

I2C uses two shared wires with addressing for multi-device support, while SPI uses separate chip-select lines per device and is faster. I2C is common for sensors and low-speed devices; SPI is common for flash, displays, and high-throughput ADCs.

Q: What are CPOL and CPHA?

CPOL is clock polarity — whether the idle state of the clock is low or high. CPHA is clock phase — whether data is sampled on the first or second clock edge. Together they define four SPI modes (0-3). The device datasheet specifies the required mode.

Q: When would you choose SPI over I2C?

When speed matters (SPI can run at tens of MHz vs I2C’s typical 400kHz), when full-duplex operation is needed, or when the device requires it. I2C is preferred when minimizing wire count is more important than speed.

Q: What is spi_message and spi_transfer?

A spi_transfer describes one segment of data exchange (tx buffer, rx buffer, length). A spi_message is a list of transfers that the controller executes atomically on the bus. spi_sync() blocks until the entire message completes.

DAY 37: BUILDROOT AND YOCTO BASICS

Theory: What Problem Do They Solve?

When building an embedded Linux system, you need to produce:

What you need for a running embedded Linux system:
  1. Cross-compilation toolchain   (GCC, binutils, libc for target arch)
  2. Bootloader binary             (U-Boot or similar)
  3. Linux kernel image + DTB      (bzImage/zImage + .dtb)
  4. Root filesystem               (BusyBox tools, libraries, app binaries)

Without a build system: building these manually takes days and is fragile.
With Buildroot or Yocto: automated, reproducible builds.

Theory: Buildroot

Buildroot is a simple, Makefile-based build system for generating complete embedded Linux systems.

What it does: - Downloads source code for all components - Cross-compiles them for your target architecture - Produces a bootable image you can flash to a board

Key concepts:

make menuconfig       → configure target arch, packages, kernel version
make                  → build everything
output/images/        → where kernel, DTB, rootfs image appear
output/target/        → the root filesystem tree
output/staging/       → sysroot for cross-compilation

Board support:
  board/<vendor>/<board>/ → board-specific configs and patches

Strengths: Simple, fast to learn, fast to build, good for small systems. Limitations: Not designed for large product lines, limited customization per-package.

Theory: Yocto Project

Yocto is a set of tools and processes for creating custom Linux distributions for embedded systems. It uses the BitBake build engine and OpenEmbedded layer system.

Key concepts:

Layer        → a set of recipes (meta-*, meta-mylayer)
Recipe (.bb) → build instructions for one package
BitBake      → the build engine that processes recipes
Image        → a collection of packages baked into a rootfs
MACHINE      → the target hardware description
DISTRO       → the Linux distribution configuration

bitbake core-image-minimal   → build a minimal image
bitbake -c devshell <recipe> → debug a recipe

Strengths: Highly customizable, reproducible, scales to product lines, industry standard for commercial embedded Linux. Limitations: Steep learning curve, slow initial builds (can take hours).

Theory: Buildroot vs Yocto — When to Use Which

Aspect Buildroot Yocto
Learning curve Low High
Build time Fast (minutes) Slow (hours first time)
Customization Moderate Extensive
Package ecosystem Good Very large (OpenEmbedded)
Best for Prototypes, simple products Complex products, multiple boards
Industry usage Widely used Industry standard for products

Interview answer: “Buildroot is simpler and faster to learn — I would use it for prototyping or a single-board product. Yocto is the industry standard for products that need long-term maintenance, multiple BSPs, or extensive package customization.”

Theory: How an Embedded Linux Image Is Assembled

Understanding what goes into a final image is important for interviews:

Embedded Linux image components:

  Toolchain → gcc + glibc/musl/uclibc for target arch
               builds everything else

  Bootloader → U-Boot binary
               initialized by BootROM, loads kernel

  Kernel     → Linux vmlinuz or zImage
               compressed, decompresses itself at boot

  DTB        → Device Tree Blob (.dtb)
               hardware description passed to kernel by bootloader

  rootfs     → root filesystem image (ext4, squashfs, ubifs, cramfs)
               contains: BusyBox (sh, ls, mount...), libraries, apps, /etc, /dev

  Optional:
    initramfs → small root filesystem baked into kernel or separate
                used for early boot or minimal recovery systems

Theory: BusyBox

BusyBox is a single binary that provides a minimal implementation of dozens of Unix utilities (sh, ls, cat, mount, ifconfig, etc.). It is the standard shell and tool provider in most embedded Linux root filesystems.

/bin/busybox -> symlinked as /bin/sh, /bin/ls, /bin/cat, etc.
Each symlink invokes BusyBox with a different argv[0] → different behavior

Interview Questions — Buildroot and Yocto

Q: What is Buildroot?

Buildroot is a Makefile-based build system that generates a complete embedded Linux system — toolchain, bootloader, kernel, and root filesystem — for a target hardware platform. It is simple to use and good for prototyping or single-board products.

Q: What is Yocto?

Yocto is a set of tools and metadata for creating custom embedded Linux distributions. It uses BitBake as the build engine and organizes packages into layers. It is the industry standard for commercial embedded Linux products because of its scalability and reproducibility.

Q: What is BusyBox?

BusyBox is a single binary that provides minimal implementations of dozens of Unix utilities. It is the standard tool provider in embedded Linux root filesystems because it occupies far less space than full GNU tools.

Q: What is the relationship between kernel, DTB, and rootfs?

The bootloader loads the kernel image and DTB into memory and passes the DTB address to the kernel at boot. The kernel uses the DTB to discover hardware. After kernel initialization, it mounts the rootfs and launches the init process. All three must be compatible — a kernel and DTB mismatch causes boot failures.

Q: What is initramfs?

initramfs is a small root filesystem embedded in or loaded alongside the kernel image. The kernel mounts it as an initial root filesystem during boot to perform early setup before switching to the real root filesystem.

DAY 38: DEBUGGING WORKFLOW DAY

Overview

Today is entirely practical. Work through each scenario systematically. The goal is to build confident debugging instincts — not memorize answers.

Scenario 1: Module Does Not Load

Symptoms: insmod or modprobe fails immediately.

Debug flow:

1. Run insmod, capture output
2. dmesg | tail -20                    → first place to check
3. Look for: vermagic mismatch         → built against wrong kernel headers
               unresolved symbol       → missing kernel config or missing module_init
               bad parameter           → wrong module_param type
               init returned error     → bug in module_init()
4. modinfo <module.ko>                 → check vermagic, dependencies, parameters
5. uname -r                           → compare to kernel headers used
6. ls /lib/modules/$(uname -r)/       → check headers are installed

Common cause: Module compiled against different kernel version than running kernel.

Scenario 2: Module Loads, But probe() Never Called

Symptoms: lsmod shows the module, but device never initializes.

Debug flow:

1. dmesg | grep <driver_name>          → any registration or matching messages?
2. cat /sys/bus/platform/devices/      → list platform devices
3. cat /sys/bus/i2c/devices/           → list I2C devices
4. Check DT node:
   - status = "okay"?
   - compatible string exactly matches of_match_table?
   - address/reg correct?
5. ls /sys/bus/platform/drivers/       → is driver registered?
6. Check that MODULE_DEVICE_TABLE is present

Common causes: - compatible string typo (case-sensitive) - DT node has status = "disabled" - Driver registered on wrong bus type - Dependency causing -EPROBE_DEFER

Scenario 3: probe() Called, But Fails

Symptoms: dmesg shows probe called, then error returned.

Debug flow:

1. dmesg | grep -i "probe\|error\|fail\|defer"
2. Add pr_err() logs around each step in probe()
3. Check: devm_kzalloc return        → -ENOMEM if out of memory
            devm_ioremap_resource    → bad reg in DT?
            platform_get_irq         → IRQ not in DT?
            clk_get / regulator_get  → dependency not ready? → EPROBE_DEFER
4. Return -EPROBE_DEFER if dependency not ready (not hard failure)

Common causes: - Wrong DT reg property (address or size mismatch) - Dependency (clock, regulator, GPIO) not yet available — return -EPROBE_DEFER - Hardware initialization sequence incorrect

Scenario 4: Device Node Not Created Under /dev

Symptoms: Driver loads and probe succeeds, but /dev/mydevice is missing.

Debug flow:

1. dmesg → did alloc_chrdev_region succeed?
2. Check: alloc_chrdev_region return value
            cdev_add return value
            class_create return value
            device_create return value
3. ls /sys/class/<classname>/        → class exists?
4. ls /proc/devices                  → character device registered?
5. Check if udev/mdev is running     → device node created by userspace daemon

Note: device_create() creates the sysfs entry. The device node in /dev is created by udev (or mdev) in response. If udev is not running, create the node manually: mknod /dev/mydevice c <major> <minor>.

Scenario 5: read() Blocks Forever

Symptoms: User application calling read() hangs and never returns.

Debug flow:

1. strace ./app                       → see which syscall is blocking
2. cat /proc/<pid>/status             → check process state (S = sleeping)
3. In driver: add pr_debug() at:
     - entry to read()
     - before wait_event_interruptible()
     - after wakeup
     - in the write path or interrupt handler (who wakes the reader?)
4. Is the wakeup condition ever set? Check the producer path.
5. Is wake_up_interruptible() called after setting the flag?
6. Check: flag set and wake_up called while holding the wrong lock?
             wake_up called before wait_event — race condition?

Common cause: The flag that signals data-ready is never set, or wake_up_interruptible() is never called.

Scenario 6: IRQ Not Firing

Symptoms: Interrupt-driven code never executes the handler.

Debug flow:

1. cat /proc/interrupts               → does the IRQ line appear?
                                        is the count incrementing?
2. request_irq/request_threaded_irq return value → 0 means success
3. dmesg → "irq request failed"?
4. Check DT: interrupts property correct?
              interrupt-parent pointing to right controller?
              trigger type matches hardware (edge vs level, polarity)?
5. Is hardware interrupt generation actually enabled?
   (check device register that enables the IRQ line)
6. pinctrl: is the IRQ pin configured as an input?

Common cause: Hardware must be configured to generate the interrupt, not just the driver. The device register that enables interrupt output is often overlooked.

Scenario 7: I2C Communication Fails

Symptoms: i2c_smbus_read_* or i2c_smbus_write_* returns negative error code.

Debug flow:

1. i2cdetect -y <bus_number>          → does device ACK at expected address?
2. dmesg | grep i2c                   → timeout or NACK messages?
3. Check:
   - correct bus number in DT?
   - correct I2C address in DT?
   - physical pull-up resistors on SDA/SCL? (if real hardware)
   - device powered and reset deasserted?
4. i2cget -y <bus> <addr> <reg>       → manual register read test
5. i2cdump -y <bus> <addr>            → dump all registers
6. Check endianness: i2c_smbus_read_word_data returns little-endian,
   but many sensors send big-endian — use swab16() if needed

Common cause: Wrong bus number, wrong address, missing pull-ups on real hardware, or register access pattern mismatch (8-bit vs 16-bit register addresses).

Must-Know Debug Commands — Reference Card

# Module loading
dmesg | tail -30                      # Check for load errors
lsmod | grep <name>                   # Is module loaded?
modinfo <module.ko>                   # Check vermagic and deps
modprobe --show-depends <module>      # Show dependency chain

# Device and driver binding
ls /sys/bus/platform/devices/         # Platform devices
ls /sys/bus/i2c/devices/              # I2C devices
ls /sys/bus/platform/drivers/         # Registered platform drivers
cat /sys/bus/platform/drivers/<drv>/uevent   # Driver info
ls /sys/bus/platform/devices/<dev>/driver    # Is device bound?

# Character devices
cat /proc/devices                     # Major number allocation
ls /sys/class/<classname>/            # Class devices

# Interrupts
cat /proc/interrupts                  # IRQ list and counts
cat /proc/irq/<irq>/spurious          # Spurious IRQ stats

# Runtime
strace -e read,write,ioctl ./app      # Trace syscalls
cat /proc/<pid>/status                # Process state

DAY 39: RESUME AND PROJECT STORY

Your Three Projects

By this point you should have working code for all three. If any project is incomplete, today is the day to finish it.

Project 1: Character Device Driver

One-line description:

“Multi-instance character device driver with IOCTL interface, blocking read via wait queue, non-blocking mode support, and sysfs attributes.”

Architecture walkthrough (2 minutes):

“I built a character device driver that exposes /dev/chardevN nodes. The driver uses alloc_chrdev_region to get a range of device numbers, and container_of in the open callback to recover per-device state from the cdev embedded in my device struct. Read and write use copy_to_user / copy_from_user for safe kernel-user transfer. For blocking read, if no data is available the reader sleeps on a wait queue using wait_event_interruptible, and wakes up when data is written. I added two IOCTL commands using _IOR and _IOW macros. A mutex protects the internal buffer. I tested it with a userspace application using both blocking and O_NONBLOCK modes.”

Key design decisions: - container_of for multi-instance: each file open recovers its own struct my_dev from the embedded cdev - wait_event_interruptible so the reader can be interrupted by signals - mutex_lock_interruptible so open/read/write are cancellable - devm_* APIs to simplify cleanup

One debugging story:

“When I first implemented the wait queue, read() returned immediately even when the buffer was empty. I had the condition check inverted — I was waking up when the buffer was empty instead of when it had data. I added pr_debug() inside the wait condition and saw it evaluating wrong. One-line fix: wait_event_interruptible(wq, buffer_len > 0) instead of == 0.”

Project 2: Platform Driver / Device Tree Demo

One-line description:

“Platform driver with DT matching, MMIO register access, IRQ handling, and devm resource management.”

Architecture walkthrough (2 minutes):

“I wrote a platform driver that matches via a DT compatible string. In probe(), I use devm_platform_ioremap_resource() to map the MMIO register range and platform_get_irq() to get the interrupt number. I request a threaded IRQ using request_threaded_irq so the heavy IRQ handling happens in a schedulable thread. The of_property_read_u32() API reads configuration from the DT node. All resources use devm_* APIs so cleanup is automatic on driver unload or probe failure.”

Key design decisions: - devm_* APIs eliminate manual cleanup paths - Threaded IRQ: top half acknowledges interrupt only, bottom thread handles data - -EPROBE_DEFER returned if clock or GPIO dependency is not ready

Project 3: I2C Sensor Driver

One-line description:

“I2C temperature sensor driver with DT matching, register I/O via SMBus, hwmon subsystem integration, and 1-second value caching.”

Architecture walkthrough (2 minutes):

“I wrote an I2C driver for a TMP102-style temperature sensor. The DT node carries the compatible string and I2C address; the kernel matches this to my driver and calls probe(). I use i2c_smbus_read_word_swapped() to read the temperature register since the sensor sends big-endian 16-bit data. I cache the last reading for 1 second to avoid flooding the I2C bus on repeated sysfs reads. The driver registers with the hwmon subsystem using devm_hwmon_device_register_with_info(), exposing the temperature through /sys/class/hwmon/hwmonN/temp1_input in millidegrees Celsius.”

One debugging story:

“Temperature readings were always off by a factor of 16. After looking at the datasheet more carefully, I realized the sensor returns the raw ADC value left-shifted by 4 — I was missing a right-shift by 4 before scaling. pr_debug("raw=0x%04x\n", raw_val) showed me 0x0c80 when the temperature should have been 0xc8 — the extra nibble at the bottom was the problem.”

OPTIONAL BONUS: THREAD POOL PROJECT

The thread pool project is not required for fresher embedded Linux roles. It is included here as an optional exercise for candidates who have extra time and want to demonstrate broader systems programming skills.

For most embedded Linux interviews, your three driver projects (character driver, platform driver, I2C driver) are the right focus. Interviewers care more about whether you understand kernel-driver basics and can debug logically than whether you built a userspace thread pool.

If you want to build the thread pool, the complete implementation (header, implementation, test application, Makefile) is available for reference. The key concepts it demonstrates are:

  • Producer-consumer pattern with condition variables
  • Spurious wakeup handling with while-loop conditions
  • Graceful shutdown with broadcast to all workers
  • Two condition variables: not_empty for workers, all_done for pool_wait()

These concepts translate directly to kernel concepts: wait queues replace condition variables, workqueues replace worker threads, and kernel synchronization patterns follow the same producer-consumer logic.

  • You built working code
  • You understand kernel-driver basics

  • You can explain your projects clearly

Three projects you can explain in depth beat ten projects you cannot discuss.
