EMBEDDED LINUX INTERVIEW PRACTICE GUIDE

Spoken Answers — Short / Deep / Follow-Up Format

How To Use This Guide

Use each question in 3 rounds:

  1. Read the Short Answer and say it in your own words in 20 seconds.
  2. Read the Deep Answer and add the extra detail only if the interviewer asks more.
  3. Practice the Follow-Up Questions without looking at the answers.

Do not memorize word-for-word. The goal is to sound clear, calm, and technically correct.

SECTION 1: C FUNDAMENTALS

Q1. What is the difference between an array and a pointer in C?

Short Answer

An array is a fixed-size contiguous collection of elements, while a pointer is a variable that stores an address. Arrays often decay to pointers when passed to functions, but they are not the same thing.

Deep Answer

If int arr[10];, then arr is storage for 10 integers. If int *p = arr;, then p only stores the address of the first element. sizeof(arr) gives the total size of the array, but sizeof(p) gives the size of the pointer itself. This matters in embedded and kernel code because confusing arrays and pointers often leads to buffer bugs.

Follow-Up Questions

  • What does array-to-pointer decay mean?
  • What is the difference between sizeof(arr) and sizeof(p)?
  • Why is this important in function parameters?

Q2. What is volatile and why is it important in embedded systems?

Short Answer

volatile tells the compiler that a variable may change unexpectedly, so it must not optimize away accesses to it. It is commonly used for hardware registers and variables affected by interrupts.

Deep Answer

In embedded programming, hardware registers can change outside normal program flow, so repeated reads must actually happen. volatile prevents the compiler from caching or removing those reads and writes. But volatile is not a lock, does not make code thread-safe, and does not replace proper synchronization.

Follow-Up Questions

  • Where would you use volatile?
  • Why is volatile not enough for multithreading?
  • Should every shared variable be volatile?

Q3. What is structure padding and alignment?

Short Answer

Compilers insert padding inside structures so members are aligned according to architecture rules. This improves access efficiency but may make the structure bigger than the sum of its fields.

Deep Answer

For example, an int may require 4-byte alignment, so if a char appears before it, the compiler may insert extra bytes in between. This matters in embedded systems when working with hardware registers, binary protocols, or DMA descriptors. If you ignore padding, you may misread data layouts or corrupt protocol structures.

Follow-Up Questions

  • Why does the compiler add padding?
  • How can you inspect structure size?
  • When is packed layout needed, and what are the risks?

Q4. What are function pointers, and why are they important in Linux kernel code?

Short Answer

A function pointer stores the address of a function and lets code call it indirectly. The kernel uses them heavily for callbacks and operation tables.

Deep Answer

In Linux drivers, structures like file_operations contain function pointers for open, read, write, ioctl, and poll. This allows the kernel to call driver-specific behavior through a common interface. Function pointers are also used in interrupt handlers, timers, workqueues, and many subsystems.

Follow-Up Questions

  • Where do function pointers appear in drivers?
  • Why are they better than a giant switch in many designs?
  • What is the syntax for a simple function pointer?

SECTION 2: LINUX FUNDAMENTALS

Q5. What is the difference between user space and kernel space?

Short Answer

User space runs normal applications with restricted privileges, while kernel space runs the operating system core and drivers with full hardware access.

Deep Answer

This separation improves security and stability. Applications cannot directly touch hardware or kernel memory; they must go through system calls. Drivers live in kernel space because they need direct access to devices, interrupts, memory-mapped I/O, and privileged kernel APIs.

Follow-Up Questions

  • Why is this separation necessary?
  • How does user space request kernel services?
  • What happens if kernel code has a bug?

Q6. What is a system call?

Short Answer

A system call is the controlled interface through which a user-space program requests a service from the kernel.

Deep Answer

Examples include open, read, write, mmap, fork, and ioctl. When a program makes a system call, the CPU switches into kernel mode, the kernel validates the request, performs the operation, and then returns back to user space. In driver interviews, this is important because user programs reach drivers through kernel-managed interfaces like file operations.

Follow-Up Questions

  • What is the path from read() in user space to a driver?
  • Why can’t user space directly call kernel functions?
  • What is ioctl() used for?

Q7. What is the difference between a process and a thread?

Short Answer

A process has its own virtual address space, while threads within the same process share memory and resources but have separate stacks and registers.

Deep Answer

Processes are heavier because they isolate memory and resources. Threads are lighter and useful when tasks within one application need to run concurrently and share data. In interviews, this question often leads into synchronization, race conditions, and the mapping between user-space threads and kernel concurrency concepts.

Follow-Up Questions

  • Why are threads lighter than processes?
  • What resources are shared between threads?
  • When would you prefer threads over processes?

Q8. Explain fork(), exec(), and copy-on-write.

Short Answer

fork() creates a new process, exec() replaces the current process image with a new program, and copy-on-write is the optimization that makes fork() efficient.

Deep Answer

After fork(), parent and child initially share the same memory pages as read-only. If either side writes to a page, the kernel creates a private copy of that page. exec() does not create a new process; it replaces the current program with a different executable. These concepts matter in Linux fundamentals and show how the kernel manages process creation efficiently.

Follow-Up Questions

  • What stays the same after exec()?
  • Why is fork() not as expensive as a full memory copy?
  • What is a typical fork() + exec() workflow?

Q9. What is the difference between mmap() and ioremap()?

Short Answer

mmap() is a user-space system call for mapping memory into a process address space, while ioremap() is a kernel function used by drivers to map physical I/O memory into kernel virtual address space.

Deep Answer

mmap() is often used for files, shared memory, and sometimes device memory exposed to user space. ioremap() is used inside drivers for accessing MMIO registers of hardware devices. Both deal with mapping memory, but they operate in different contexts and for different users.

Follow-Up Questions

  • Why can’t a driver directly dereference a physical address?
  • Where would mmap() appear in a character driver?
  • What APIs are used after ioremap()?

Q10. Explain the embedded Linux boot flow.

Short Answer

A typical embedded Linux boot flow is: BootROM → bootloader like U-Boot → kernel → initramfs or root filesystem → init process.

Deep Answer

The SoC starts with BootROM, which loads a bootloader from flash, SD, or another source. The bootloader initializes basic hardware, loads the kernel image, Device Tree Blob, and sometimes initramfs, and passes boot arguments. Then the kernel initializes subsystems, mounts a temporary or final root filesystem, and starts init or another first userspace process.

Follow-Up Questions

  • What does U-Boot do?
  • What is initramfs?
  • What is the role of the Device Tree Blob?

SECTION 3: KERNEL MODULES AND KERNEL MEMORY

Q11. What is a kernel module?

Short Answer

A kernel module is code that can be loaded into or removed from the kernel at runtime.

Deep Answer

Modules are commonly used for device drivers, filesystems, and protocol support. They let you add functionality without rebuilding the entire kernel. A module usually has an initialization function and an exit function, declared using module_init() and module_exit().

Follow-Up Questions

  • What is the difference between a built-in driver and a module?
  • Why are modules useful during development?
  • What commands are used to load and unload a module?

Q12. What is the difference between insmod and modprobe?

Short Answer

insmod loads a module directly by filename, while modprobe loads a module by name and also resolves dependencies automatically.

Deep Answer

insmod is a simple low-level tool and does not handle dependencies. modprobe consults module dependency information and is generally the preferred command on real systems. If a module fails to load, dmesg is often the first place to check for errors like unresolved symbols or vermagic mismatch.

Follow-Up Questions

  • What is vermagic?
  • Why might a module fail to load?
  • When would you use modprobe instead of insmod?

Q13. What is the difference between kmalloc(), kzalloc(), and vmalloc()?

Short Answer

kmalloc() allocates physically contiguous memory, kzalloc() does the same but zero-initializes it, and vmalloc() allocates virtually contiguous memory that may not be physically contiguous.

Deep Answer

kmalloc() is the most common allocator for small driver structures. kzalloc() is often preferred because it avoids uninitialized fields. vmalloc() is useful for larger allocations where physical contiguity is not required, but it is slower and unsuitable for many DMA use cases.

Follow-Up Questions

  • Why is physical contiguity sometimes important?
  • When would vmalloc() be a bad choice?
  • Why is kzalloc() often safer than kmalloc()?

Q14. What are GFP_KERNEL and GFP_ATOMIC?

Short Answer

They are memory allocation flags. GFP_KERNEL is used when sleeping is allowed, and GFP_ATOMIC is used when sleeping is not allowed.

Deep Answer

GFP_KERNEL is the normal choice in process context because the allocator may block and reclaim memory. GFP_ATOMIC is used in interrupt context or while holding a spinlock, where sleeping would be illegal. Using the wrong flag can lead to failures or serious kernel bugs.

Follow-Up Questions

  • In which context is GFP_ATOMIC required?
  • Why can’t allocation sleep in interrupt context?
  • What is process context versus atomic context?

Q15. Why does kernel code often use goto for cleanup?

Short Answer

Kernel code uses goto cleanup to handle errors cleanly when multiple resources are allocated in sequence.

Deep Answer

If a driver allocates memory, maps registers, requests an IRQ, and then fails later, it must release earlier resources in reverse order. Without goto, cleanup logic gets duplicated and becomes error-prone. The goto cleanup pattern centralizes resource release and makes failure paths easier to maintain.

Follow-Up Questions

  • Why is this pattern common in probe()?
  • Why is duplicated cleanup code risky?
  • How do devm_* APIs reduce cleanup code?

SECTION 4: CHARACTER DRIVER

Q16. What is a character device driver?

Short Answer

A character device driver provides stream-oriented access to a device through file operations such as open, read, write, and ioctl.

Deep Answer

Character devices are exposed through device nodes under /dev. User space interacts with them using normal file APIs, and the kernel routes those operations into the driver’s file_operations table. Many custom embedded drivers begin as character drivers because they are simple and flexible.

Follow-Up Questions

  • What is the difference between character and block devices?
  • Where does the device node come from?
  • Why are character drivers common in teaching and interviews?

Q17. What are major and minor numbers?

Short Answer

The major number identifies the driver, and the minor number identifies a specific device instance handled by that driver.

Deep Answer

This allows one driver to manage multiple devices. The device number is stored in dev_t, and helper macros like MAJOR(), MINOR(), and MKDEV() are used to work with it. In a multi-instance driver, the minor number often helps locate per-device private data.

Follow-Up Questions

  • What is dev_t?
  • How do you allocate device numbers?
  • How can one driver support multiple devices?

Q18. What are cdev and file_operations?

Short Answer

cdev represents a character device in the kernel, and file_operations is the table of callbacks that defines how that device behaves.

Deep Answer

When user space opens a device node, the VFS uses the registered cdev to find the driver’s file_operations. These callbacks implement methods like open, release, read, write, unlocked_ioctl, and poll. This is one of the most important driver concepts to understand clearly for interviews.

Follow-Up Questions

  • What callback is called when a user runs read()?
  • Where is the driver’s private state usually stored?
  • Why are function pointers central here?

Q19. Why do drivers use copy_to_user() and copy_from_user()?

Short Answer

Drivers use them to safely transfer data between kernel space and user space.

Deep Answer

The kernel cannot trust or directly dereference user pointers because user memory may be invalid, unmapped, or malicious. copy_to_user() and copy_from_user() perform controlled access across the boundary. This is a very common interview question because it checks whether you understand the user-kernel memory separation.

Follow-Up Questions

  • Why is direct access to user pointers unsafe?
  • What happens if the copy fails?
  • Where would you use these functions in a character driver?

Q20. What is ioctl() and when would you use it?

Short Answer

ioctl() is used for device-specific control operations that do not fit naturally into read() or write().

Deep Answer

Examples include resetting a device, changing configuration, reading status, or issuing commands. In Linux drivers, ioctl commands are usually defined with macros like _IO, _IOR, and _IOW. Good drivers use ioctl() only when the operation really is control-oriented and does not map well to data streaming.

Follow-Up Questions

  • What is the difference between _IO, _IOR, and _IOW?
  • When should you avoid ioctl()?
  • Could sysfs be a better choice in some cases?

Q21. How do you implement a blocking read() in a driver?

Short Answer

If data is not available, the process sleeps on a wait queue until the device or another context makes data available and wakes it up.

Deep Answer

A blocking read() should not spin in a loop. Instead, it should check whether data is available, call wait_event_interruptible() or a similar API if not, and wake up later when the condition becomes true. This is a core driver concurrency pattern and is far more interview-relevant than advanced user-space thread pools.

Follow-Up Questions

  • What is a wait queue?
  • Why is blocking better than busy-waiting?
  • What should happen if the process receives a signal while waiting?

Q22. What is .poll() in a driver?

Short Answer

.poll() reports whether a device is ready for reading, writing, or other events, enabling user-space APIs like poll(), select(), and epoll().

Deep Answer

The driver’s .poll() implementation typically registers a wait queue and returns a bitmask indicating readiness. This lets user space efficiently monitor multiple descriptors instead of blocking blindly on one read(). If you add blocking I/O to a character driver, knowing how .poll() fits in is a strong plus in interviews.

Follow-Up Questions

  • How is .poll() different from read()?
  • What does O_NONBLOCK change?
  • Why is .poll() useful in real applications?

SECTION 5: DEVICE TREE AND PLATFORM DRIVER

Q23. Why does Device Tree exist?

Short Answer

Device Tree separates hardware description from driver code so the same kernel can work across multiple boards without hardcoding platform details into drivers.

Deep Answer

Instead of embedding addresses, IRQs, GPIOs, clocks, and compatible strings directly in code, those details are described in a data structure that the kernel parses at boot. Drivers then match devices using compatible strings and fetch resources from the tree. This is essential in embedded Linux, especially on ARM-based systems.

Follow-Up Questions

  • What hardware details are typically stored in DT?
  • What is a compatible string?
  • Why is this approach better than hardcoded board files?

Q24. What is a compatible string, and how does matching happen?

Short Answer

A compatible string identifies the hardware type, and the kernel matches it against a driver’s of_match_table.

Deep Answer

For example, a DT node may contain compatible = "vendor,my-device";. The driver exposes a list of supported strings, and if a match is found, the kernel binds the device to that driver and calls probe(). If the strings do not match exactly, probe() will never be called.

Follow-Up Questions

  • What should you check if probe() is not called?
  • Can one driver support multiple compatible strings?
  • How does this differ from I2C device ID matching?

Q25. What are the reg, interrupts, and phandle-style properties used for?

Short Answer

reg describes memory-mapped register ranges, interrupts describes interrupt wiring, and phandle references connect one DT node to another resource provider like a GPIO controller or clock provider.

Deep Answer

A driver uses these properties to discover hardware resources without hardcoding them. For example, reg is used with resource mapping APIs, interrupts leads to IRQ lookup, and a phandle may connect the device to clocks, regulators, GPIO controllers, or pinctrl settings. Understanding these properties makes DT discussions much easier in interviews.

Follow-Up Questions

  • How does a driver get the register base from reg?
  • How does a driver get an IRQ from the DT?
  • What kinds of things are usually referenced by phandles?

Q26. What is a platform driver, and what usually happens in probe()?

Short Answer

A platform driver handles non-discoverable SoC or board-integrated devices, and probe() is where the driver acquires resources, initializes hardware, and registers its interfaces.

Deep Answer

In probe(), a platform driver commonly allocates private data, maps MMIO registers with devm_platform_ioremap_resource(), gets IRQs with platform_get_irq(), requests clocks or GPIOs, initializes the device, and registers with a subsystem or creates user interfaces. If something fails, it returns an error and performs cleanup or relies on devm_* helpers.

Follow-Up Questions

  • What kinds of devices use platform drivers?
  • What is devm_platform_ioremap_resource()?
  • Why is probe() such an important function?

Q27. What is -EPROBE_DEFER and when is it used?

Short Answer

-EPROBE_DEFER tells the kernel that a driver’s dependency is not ready yet and that probing should be tried again later.

Deep Answer

This happens when a device depends on another provider such as a clock, regulator, GPIO controller, reset controller, or other subsystem that has not finished registering. Returning -EPROBE_DEFER is the correct way to handle this dependency ordering issue.

Follow-Up Questions

  • What dependencies commonly cause deferred probing?
  • Why is returning a hard failure wrong in this case?
  • How would you debug repeated probe deferrals?

SECTION 6: I2C AND SPI

Q28. What is the difference between I2C and SPI?

Short Answer

I2C uses two shared wires and addressing, while SPI uses separate clock/data lines and chip-select signals and is usually faster.

Deep Answer

I2C is common for sensors, EEPROMs, RTCs, and low-speed peripherals because it uses fewer wires and allows multiple devices on the same bus by address. SPI is often used for flash, displays, ADCs, and other higher-speed devices because it offers higher throughput. Interviewers often ask this to see if you can choose the right bus for a use case.

Follow-Up Questions

  • When would you choose I2C over SPI?
  • What are ACK and NACK in I2C?
  • What are CPOL and CPHA in SPI?

Q29. Explain the Linux I2C model: adapter, client, and driver.

Short Answer

The adapter is the I2C controller, the client is a device on the bus, and the driver is the software that handles that device.

Deep Answer

The adapter represents the hardware bus controller. The client represents a specific device at a specific address on that bus. The driver binds to that client, typically through Device Tree matching, and uses APIs like i2c_smbus_read_byte_data() or i2c_smbus_write_byte_data() to talk to the device.

Follow-Up Questions

  • What is an i2c_client?
  • How does DT matching work for I2C drivers?
  • What are SMBus helper APIs?

Q30. Why is subsystem integration like hwmon preferred in sensor drivers?

Short Answer

Subsystem integration gives a standard user-space interface and makes drivers more maintainable and consistent with the rest of Linux.

Deep Answer

Instead of inventing a custom /dev interface or custom sysfs layout, a temperature sensor driver can register with hwmon, which automatically exposes standard attributes like temp1_input. This is better for tooling, userspace compatibility, and code quality.

Follow-Up Questions

  • What kinds of subsystems exist besides hwmon?
  • Why is a subsystem often better than a custom character device?
  • What does a sensor driver still need to implement after joining hwmon?

SECTION 7: CONCURRENCY, INTERRUPTS, AND DRIVER CONTEXT

Q31. What is the difference between process context and interrupt context?

Short Answer

Process context is normal schedulable task context where sleeping is usually allowed, while interrupt context is time-sensitive and must not sleep.

Deep Answer

Code running due to system calls, kernel threads, or workqueues usually runs in process context. Interrupt handlers run in interrupt context and must complete quickly because they are handling urgent events. This distinction determines what locks, memory allocation flags, and APIs are safe to use.

Follow-Up Questions

  • Why can’t you sleep in interrupt context?
  • Which allocation flags are safe in interrupt context?
  • Is a workqueue process context or interrupt context?

Q32. What is the difference between a mutex and a spinlock?

Short Answer

A mutex is a sleeping lock used in process context, while a spinlock is a busy-wait lock used when sleeping is not allowed, such as atomic or interrupt context.

Deep Answer

Use a mutex for longer critical sections where blocking is acceptable. Use a spinlock for short critical sections where the code cannot sleep. A common interview trap is to ask whether a mutex can be used in interrupt context; the correct answer is no, because mutex acquisition may sleep.

Follow-Up Questions

  • Why is sleeping while holding a spinlock wrong?
  • When would you use spin_lock_irqsave()?
  • If data is shared between process context and IRQ context, what kind of protection is common?

Q33. What are top half, threaded IRQ, and workqueue?

Short Answer

The top half is the immediate interrupt handler, a threaded IRQ defers heavier work to a schedulable thread, and a workqueue defers work to process context.

Deep Answer

A top half should do only urgent work like acknowledging the interrupt and capturing minimal state. If more work is needed and it may sleep, a threaded IRQ or workqueue is used. Modern driver design often prefers a small hard IRQ handler plus a threaded IRQ handler, because real device handling often needs APIs that are not safe in hard interrupt context.

Follow-Up Questions

  • Why should the top half be short?
  • When would you prefer threaded IRQ over workqueue?
  • Can a threaded IRQ sleep?

SECTION 8: DEBUGGING AND PROJECT DISCUSSION

Q34. How would you debug if your driver’s probe() is not getting called?

Short Answer

First check whether the driver loaded, whether the DT compatible string matches, and whether the device node is enabled.

Deep Answer

A practical debug flow is: - check dmesg for driver registration logs - verify the DT node exists and has status = "okay" - confirm the compatible string exactly matches the driver’s of_match_table - confirm the driver is registered on the right bus - check whether dependencies are causing -EPROBE_DEFER

Follow-Up Questions

  • What if the module loaded but probe() still never runs?
  • How would you detect repeated probe deferral?
  • What sysfs paths can help inspect device-driver binding?

Q35. How would you debug a module that fails to load?

Short Answer

Start with dmesg, then check for symbol errors, vermagic mismatch, invalid parameters, missing dependencies, or code paths that fail during initialization.

Deep Answer

Many module load problems are explained clearly in kernel logs. Common causes include unresolved symbols, wrong kernel version, missing exported symbols, bad module parameters, or crashes during init. The key interview point is not memorizing every failure, but showing that your first move is to inspect logs and reason systematically.

Follow-Up Questions

  • What is vermagic mismatch?
  • What is the difference between insmod failure and runtime probe failure?
  • Why is dmesg usually the first step?

Q36. Walk me through your driver project.

Short Answer

Start from the user-visible goal, then explain architecture, data flow, synchronization, error handling, and how you tested and debugged it.

Deep Answer

A strong answer usually follows this structure: - what problem the driver solves - how the kernel matches or creates the device - what resources are acquired in probe() or init - how user space or a subsystem interacts with the driver - what synchronization is used and why - how errors are handled - how you tested it - one real bug you debugged

Interviewers care less about fancy wording and more about whether you truly understand your own code.

Follow-Up Questions

  • What was the hardest bug you hit?
  • Why did you choose that synchronization mechanism?
  • If you had more time, what would you improve?

SECTION 9: DEBUGGING SCENARIOS — PRACTICAL

Q1. A kernel module is not loading. How would you debug it?

Short Answer

First I would check dmesg, because kernel logs usually show the real reason such as symbol mismatch, vermagic issue, bad parameters, or init failure.

Deep Answer

My normal flow would be: - run insmod or modprobe - immediately check dmesg - verify kernel version and module vermagic - check for unresolved symbols - check whether module parameters are valid - confirm the module was built against the correct headers - if needed, inspect modinfo

In driver development, dmesg is usually the fastest way to understand why loading failed.

Follow-Up Questions

  • What is vermagic mismatch?
  • What is the difference between insmod and modprobe here?
  • What if the module loads but the device still does not work?

Q2. Your driver module loads, but probe() is never called. What would you check?

Short Answer

I would check whether the device was actually created or described correctly, whether the compatible string matches, and whether the driver is registered on the correct bus.

Deep Answer

For a DT-based embedded driver, I would verify: - the Device Tree node exists - status = "okay" - compatible matches the driver of_match_table - the bus type is correct - the module actually registered the driver successfully - there is no dependency causing deferred probe

If this is an I2C driver, I would also check whether the I2C device exists on the expected bus and address.

Follow-Up Questions

  • What is of_match_table?
  • What is -EPROBE_DEFER?
  • How would you check device-driver binding in sysfs?

Q3. probe() is called, but it fails. How would you debug that?

Short Answer

I would add clear logs inside probe() and identify exactly which resource acquisition or initialization step is failing.

Deep Answer

A structured way is: - log probe entry - log each major step - check return values after allocation, MMIO mapping, IRQ lookup, clock or GPIO acquisition - inspect PTR_ERR() values for device-managed resource failures - check DT properties carefully - verify resource order and cleanup path

Most probe failures happen due to bad DT data, missing dependencies, or incorrect assumptions about hardware state.

Follow-Up Questions

  • Which APIs in probe() commonly return error pointers?
  • Why is structured logging important?
  • Why are cleanup paths critical here?

Q4. Device node under /dev is not created. What would you check?

Short Answer

I would check whether device number allocation, cdev_add, class_create, and device_create all succeeded, and then inspect dmesg.

Deep Answer

For a character driver, the usual flow is: - allocate or register device number - initialize and add cdev - create class - create device node

If /dev entry is missing, then one of those steps likely failed. I would also check whether user-space device management like udev or mdev is present if the system depends on it.

Follow-Up Questions

  • What are major and minor numbers?
  • Does cdev_add() itself create /dev?
  • What is the role of class_create() and device_create()?

Q5. read() blocks forever in your driver. How would you debug that?

Short Answer

I would check whether the condition for waking the wait queue is ever becoming true and whether the wake-up path is actually executed.

Deep Answer

For a blocking read(), common issues are: - data-ready flag never set - wake-up function never called - wrong lock usage preventing state update - race between condition check and sleep - userspace waiting on wrong file descriptor

I would add logs around: - entering read() - checking readiness condition - sleeping on wait queue - the producer or interrupt path - the wake-up call

Follow-Up Questions

  • What is a wait queue?
  • Why must the wait condition be checked carefully?
  • How would non-blocking mode behave differently?

Q6. poll() is not working correctly. How would you think about it?

Short Answer

I would check whether the driver correctly registers the wait queue with poll_wait() and returns the right readiness mask when data is available.

Deep Answer

A .poll() bug usually comes from one of these: - wait queue not registered with poll_wait() - readiness bits not set correctly - internal state not updated properly - race between event generation and polling logic

I would verify whether the device should report readable, writable, or error conditions and whether those states match the driver’s internal buffer or event flags.

Follow-Up Questions

  • What is the difference between .poll() and read()?
  • What readiness bits are commonly returned?
  • Why is .poll() important for real applications?

Q7. Interrupt is registered, but it never fires. What would you check?

Short Answer

I would check DT interrupt configuration, hardware enable path, and /proc/interrupts to confirm whether the IRQ is actually arriving.

Deep Answer

My debug flow would be: - verify the IRQ number from DT or platform APIs - check request_irq() or request_threaded_irq() return value - confirm hardware interrupt generation is enabled in the device register - inspect /proc/interrupts - verify interrupt polarity and trigger type - check whether the interrupt line is masked - confirm pinctrl and GPIO/IRQ routing if relevant

Often the problem is not in the handler code but in DT, pin configuration, or hardware enable sequence.

Follow-Up Questions

  • What does /proc/interrupts show?
  • Why do trigger type and polarity matter?
  • What if the interrupt count increases but the handler logic still seems wrong?

Q8. Your I2C driver probes, but communication with the device fails. How do you debug it?

Short Answer

I would check bus number, device address, DT data, pull-ups, and the actual register read/write return values.

Deep Answer

Typical checks include: - i2cdetect to see whether the device responds at the expected address - DT node address and compatible string - correct bus number - physical wiring and pull-ups if real hardware is used - whether the device needs initialization before reads - whether register width and endianness are handled correctly - kernel log messages around transfer failures

I2C issues are often caused by wrong address, missing pull-ups, bad wiring, or using the wrong register access pattern.

Follow-Up Questions

  • What tools help debug I2C from Linux?
  • What is the difference between raw I2C and SMBus helper APIs?
  • Why might a sensor ACK but still return wrong data?

Q9. The kernel crashes with an oops after loading your driver. What would you do?

Short Answer

I would read the oops carefully, identify the failing function and address, and relate it to the recent code path such as probe, read, interrupt, or cleanup.

Deep Answer

I would check: - the call trace for the faulting function - the failing address (null pointer dereference is common) - whether the crash happened in init, probe, or a runtime path - recently changed code - use of uninitialized pointers - use after free

Tools like addr2line with the module’s debug symbols can convert a crash address into a source line. If a crash is reproducible, adding pr_debug() before and after suspicious lines helps narrow it down.

Follow-Up Questions

  • What is a kernel oops vs a kernel panic?
  • How would you use addr2line with a module?
  • Can the system continue after an oops?

5. One Bug You Debugged (20 seconds)

6. What You Would Improve (optional, 10 seconds)
   "If I had more time, I would [add X] because [reason]."

Character Driver Walkthrough

“I built a character device driver that exposes /dev/chardevN nodes for userspace access. The architecture uses alloc_chrdev_region for device numbers and container_of in the open callback to recover per-device state from the embedded cdev. Read and write use copy_to_user and copy_from_user for safe kernel-user transfer. Blocking read puts the reader to sleep on a wait queue using wait_event_interruptible and wakes it up when data is written. A mutex protects the internal buffer. I added IOCTL commands using _IOR and _IOW macros. The bug I hit was an inverted wait condition — I had buffer_len == 0 where I meant buffer_len > 0, so read woke immediately on empty buffer. I caught it by adding pr_debug inside the wait condition evaluation.”

Platform Driver Walkthrough

“I built a platform driver that matches a DT node by compatible string. In probe(), I use devm_platform_ioremap_resource to map MMIO registers and platform_get_irq to get the interrupt. I request a threaded IRQ so the heavy work happens in schedulable context. All resources use devm_* APIs so cleanup is automatic. The bug I hit was a -EPROBE_DEFER that was silently swallowed — I was checking the return value incorrectly and treating it as a fatal error. After I added a pr_info showing the return code, I saw it was -517 which is EPROBE_DEFER, and passing it up to the framework allowed the probe to retry successfully.”

I2C Sensor Driver Walkthrough

“I built an I2C driver for a TMP102-style temperature sensor. The DT node carries the compatible string and address, and the kernel calls my probe() on match. I read the temperature register using i2c_smbus_read_word_swapped since the sensor sends big-endian data. I cache the reading for one second to avoid flooding the bus. I registered with hwmon using devm_hwmon_device_register_with_info so the temperature appears at /sys/class/hwmon/hwmonN/temp1_input in millidegrees Celsius. The bug I hit was temperature readings 16x too large — the raw ADC value was left-shifted by 4 in the register and I forgot to right-shift before scaling. I caught it by printing the raw hex value with pr_debug.”

SECTION 11: HR AND RESUME QUESTIONS

Q: Tell me about yourself.

Structure

“I am a [background] engineer with strong C programming skills. I have spent the last [N weeks/months] preparing specifically for embedded Linux and device driver roles by [building projects]. My three main projects are [X], [Y], [Z]. I am looking for a role where I can work on [kernel/driver/embedded] development.”

Key: Mention the projects by name immediately. Interviewers for embedded roles want to know you have built something, not just studied.

Q: Why do you want to work in embedded Linux?

Good Answer

“I enjoy working close to hardware. What draws me to Linux driver development specifically is that the code directly controls physical devices — there is a clear connection between a line of code and something happening in hardware. I also find the kernel’s design — the way subsystems like I2C, hwmon, and the platform driver framework are architected — really elegant to work with.”

Key: Be specific. Mention something technical you actually found interesting.

Q: What is your biggest technical weakness?

Good Answer

“I have less hands-on experience with Yocto and BSP-level bring-up — most of my work has been at the driver level on an existing running system or QEMU. I have studied the concepts and understand the overall workflow, but I have not built a full Yocto image from scratch. I would expect to need some ramp-up time on BSP tasks.”

Key: Pick a real weakness but one that is peripheral to the core job. Show you are aware of it and working on it.

Q: Describe a time you debugged a hard problem.

Structure

“The hardest bug I hit was [symptom]. My first hypothesis was [wrong guess]. I tested that by [specific action] and it did not reproduce. I then added [specific debug logs or tool]. That showed me [specific data point]. From that I concluded [root cause]. The fix was [one sentence].”

Key: Interviewers want to see your debugging process, not just the answer. Walk through what you tried that was wrong before you found the right answer.

Q: How do you learn new technical topics?

Good Answer

“I prefer to read a short overview first to understand the problem the technology solves, then immediately try to build something small with it. For example, when I was learning the Linux I2C subsystem, I read the kernel documentation first, then built a minimal driver skeleton and tested it on i2c-stub before adding real functionality. I find building something forces me to discover the parts I do not actually understand.”

Q: Where do you see yourself in 3 years?

Good Answer

“I want to be contributing to production embedded Linux systems — ideally having worked on board bring-up, driver development, and debugging real hardware issues. I would like to have contributed upstream patches to the kernel or at least have experience working in a codebase with kernel contribution standards. I am also interested in learning more about BSP development and Yocto as I get more experience.”
